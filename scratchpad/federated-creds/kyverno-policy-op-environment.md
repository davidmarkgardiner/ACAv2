# Kyverno Policy — ServiceAccount Workload Identity Restriction per Cluster

**Purpose:** Prevent misconfiguration where a ServiceAccount on a cluster is annotated with a UAMI client-id that doesn't belong to that cluster's environment.
**Status:** Quick win — deploys to existing Kyverno installations on each cluster.

**Important scope note:** This is an anti-misconfiguration control, not an anti-attacker control. A pod can call the Azure AD token endpoint directly with a projected SA token, bypassing the annotation entirely. This layer catches human error and bad automation — not deliberate abuse.

---

## 1. Current Tagging Posture

| Resource | `op-environment` tag | Confirmed |
|---|---|---|
| AKS clusters | Yes | All clusters tagged |
| Subscriptions | Yes | All subscriptions tagged |
| User-Assigned Managed Identities | Yes | All UAMIs tagged |

**Canonical `op-environment` values:** `dev`, `pre-prod`, `prod`

Each cluster knows its environment. The approved UAMI client-id list for a cluster is derived from all UAMIs across the management group that share the same `op-environment` value.

---

## 2. Core Logic

```
ServiceAccount create/update arrives at Kyverno webhook
    |
    v
Does it have the annotation azure.workload.identity/client-id?
    --> No: ALLOW (not using workload identity)
    --> Yes: continue
    |
    v
Is the client-id in the approved list for THIS cluster's op-environment?
    --> Approved list: all UAMI client-ids where op-environment matches the cluster
    --> Stored in ConfigMap on the cluster
    --> Yes: ALLOW
    --> No: DENY ("UAMI client-id is not approved for this cluster's op-environment")
```

## 3. Generate Approved Client-ID Lists — Management Group Scope

The script queries all UAMIs across all subscriptions in the management group and groups client-ids by `op-environment`.

```bash
#!/bin/bash
# generate-approved-client-ids.sh
# Queries ALL UAMIs across a management group
# Groups client-ids by op-environment tag
# Outputs one list per environment for use in Kyverno ConfigMaps

set -euo pipefail

MGMT_GROUP="${1:?Usage: $0 <management-group-name>}"
OUTPUT_DIR="${2:-.}"

echo "=== Approved Client-ID Generator ==="
echo "Management group: ${MGMT_GROUP}"
echo ""

ALL_UAMIS="[]"

# Iterate all subscriptions in the management group
az account management-group show \
  --name "$MGMT_GROUP" \
  --expand children --recurse \
  --query "children[?type=='Microsoft.Management/managementGroups/subscriptions'].name || children[].children[?type=='Microsoft.Management/managementGroups/subscriptions'].name | []" -o tsv \
  | while read SUB_ID; do

  SUB_NAME=$(az account show --subscription "$SUB_ID" --query name -o tsv 2>/dev/null || echo "unknown")
  echo "Scanning: ${SUB_NAME} (${SUB_ID})"

  UAMIS=$(az identity list --subscription "$SUB_ID" \
    --query "[].{name:name, clientId:clientId, resourceGroup:resourceGroup, env:tags.\"op-environment\"}" \
    -o json 2>/dev/null || echo "[]")

  UAMI_COUNT=$(echo "$UAMIS" | jq length)
  echo "  Found ${UAMI_COUNT} UAMIs"

  # Warn about UAMIs missing the tag
  UNTAGGED=$(echo "$UAMIS" | jq -r '.[] | select(.env == null) | "  WARNING: \(.resourceGroup)/\(.name) has no op-environment tag"')
  if [ -n "$UNTAGGED" ]; then
    echo "$UNTAGGED"
  fi

  ALL_UAMIS=$(echo "$ALL_UAMIS" "$UAMIS" | jq -s '.[0] + .[1]')
done

# Generate per-environment lists
echo ""
echo "=== Generating approved lists ==="

for ENV in dev pre-prod prod; do
  CLIENT_IDS=$(echo "$ALL_UAMIS" | jq -r --arg env "$ENV" '[.[] | select(.env == $env) | .clientId] | sort | unique')
  COUNT=$(echo "$CLIENT_IDS" | jq length)

  echo ""
  echo "--- op-environment: ${ENV} (${COUNT} UAMIs) ---"

  # Write as newline-separated list for ConfigMap data field
  echo "$CLIENT_IDS" | jq -r '.[]' > "${OUTPUT_DIR}/approved-client-ids-${ENV}.txt"
  echo "Written to ${OUTPUT_DIR}/approved-client-ids-${ENV}.txt"

  # Write detailed inventory for audit
  echo "$ALL_UAMIS" | jq -r --arg env "$ENV" \
    '.[] | select(.env == $env) | "\(.resourceGroup)/\(.name): \(.clientId)"' \
    > "${OUTPUT_DIR}/uami-inventory-${ENV}.txt"
  echo "Written to ${OUTPUT_DIR}/uami-inventory-${ENV}.txt"
done

# Flag anomalies
echo ""
echo "=== Anomalies ==="
echo "$ALL_UAMIS" | jq -r '.[] | select(.env == null) | "NO TAG: \(.resourceGroup)/\(.name) (\(.clientId))"'
```

## 4. ConfigMap — Approved Client-IDs

Deploy one ConfigMap per cluster. The content comes from the approved list for the cluster's `op-environment`.

### Template

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: approved-workload-identity-client-ids
  namespace: kyverno
  labels:
    app.kubernetes.io/managed-by: platform-engineering
    op-environment: "${CLUSTER_ENVIRONMENT}"  # e.g. prod, pre-prod, dev
data:
  # Generated by generate-approved-client-ids.sh
  # Contains all UAMI client-ids where op-environment = ${CLUSTER_ENVIRONMENT}
  client-ids: |
    ${CLIENT_IDS_NEWLINE_SEPARATED}
```

### Generation script for a specific cluster

```bash
#!/bin/bash
# apply-approved-client-ids-configmap.sh
# Applies the approved client-id ConfigMap to a specific cluster

set -euo pipefail

CLUSTER_CONTEXT="${1:?Usage: $0 <kubectl-context> <environment>}"
ENVIRONMENT="${2:?Usage: $0 <kubectl-context> <environment>}"
APPROVED_FILE="${3:-approved-client-ids-${ENVIRONMENT}.txt}"

if [ ! -f "$APPROVED_FILE" ]; then
  echo "ERROR: ${APPROVED_FILE} not found. Run generate-approved-client-ids.sh first."
  exit 1
fi

CLIENT_IDS=$(cat "$APPROVED_FILE")
COUNT=$(wc -l < "$APPROVED_FILE" | tr -d ' ')

echo "Applying ${COUNT} approved client-ids for op-environment=${ENVIRONMENT} to cluster ${CLUSTER_CONTEXT}"

kubectl --context "$CLUSTER_CONTEXT" apply -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata:
  name: approved-workload-identity-client-ids
  namespace: kyverno
  labels:
    app.kubernetes.io/managed-by: platform-engineering
    op-environment: "${ENVIRONMENT}"
data:
  client-ids: |
$(echo "$CLIENT_IDS" | sed 's/^/    /')
EOF

echo "Done."
```

### Bulk apply across all clusters

```bash
#!/bin/bash
# apply-all-clusters.sh
# Applies the correct ConfigMap to every cluster based on its op-environment

set -euo pipefail

MGMT_GROUP="${1:?Usage: $0 <management-group-name>}"
APPROVED_DIR="${2:-.}"

az account management-group show \
  --name "$MGMT_GROUP" \
  --expand children --recurse \
  --query "children[?type=='Microsoft.Management/managementGroups/subscriptions'].name || children[].children[?type=='Microsoft.Management/managementGroups/subscriptions'].name | []" -o tsv \
  | while read SUB_ID; do

  CLUSTERS=$(az aks list --subscription "$SUB_ID" \
    --query "[].{name:name, rg:resourceGroup, env:tags.\"op-environment\"}" -o json 2>/dev/null || echo "[]")

  echo "$CLUSTERS" | jq -r '.[] | "\(.rg) \(.name) \(.env)"' | while read RG NAME ENV; do
    if [ "$ENV" = "null" ] || [ -z "$ENV" ]; then
      echo "SKIP: ${RG}/${NAME} — no op-environment tag"
      continue
    fi

    echo "Cluster: ${RG}/${NAME} [op-environment: ${ENV}]"

    # Get cluster credentials (uses current az context)
    az aks get-credentials --subscription "$SUB_ID" -g "$RG" -n "$NAME" --overwrite-existing 2>/dev/null

    ./apply-approved-client-ids-configmap.sh "$NAME" "$ENV" "${APPROVED_DIR}/approved-client-ids-${ENV}.txt"
    echo ""
  done
done
```

## 5. Kyverno ClusterPolicy

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-workload-identity-client-id
  annotations:
    policies.kyverno.io/title: Restrict Workload Identity Client-ID to Same op-environment
    policies.kyverno.io/description: >-
      Validates that ServiceAccounts annotated with azure.workload.identity/client-id
      only reference UAMI client-ids from the same op-environment as this cluster.
      Prevents cross-environment workload identity misconfiguration.
    policies.kyverno.io/category: Security
    policies.kyverno.io/severity: high
spec:
  validationFailureAction: Audit  # Start in Audit, move to Enforce after validation
  background: true  # Scan existing ServiceAccounts
  failurePolicy: Fail  # Do NOT fail-open — deny if Kyverno can't evaluate
  rules:
    - name: validate-workload-identity-client-id
      match:
        any:
          - resources:
              kinds:
                - ServiceAccount
      preconditions:
        all:
          - key: "{{ request.object.metadata.annotations.\"azure.workload.identity/client-id\" || '' }}"
            operator: NotEquals
            value: ""
      context:
        - name: approvedClientIds
          configMap:
            name: approved-workload-identity-client-ids
            namespace: kyverno
      validate:
        message: >-
          The UAMI client-id "{{ request.object.metadata.annotations."azure.workload.identity/client-id" }}"
          is not approved for this cluster's op-environment.
          Only UAMIs tagged with the same op-environment are permitted.
          Contact Platform Engineering to add this UAMI to the approved list.
        deny:
          conditions:
            all:
              - key: "{{ request.object.metadata.annotations.\"azure.workload.identity/client-id\" }}"
                operator: AnyNotIn
                value: "{{ approvedClientIds.data.\"client-ids\" | split(@, '\n') | filter(@, '') }}"
```

## 6. Hardening the ConfigMap

The ConfigMap is the trust anchor. If someone can edit it, they bypass the policy.

### RBAC: Restrict ConfigMap writes

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: approved-client-ids-writer
  namespace: kyverno
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["approved-workload-identity-client-ids"]
    verbs: ["get", "update", "patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: approved-client-ids-writer-binding
  namespace: kyverno
subjects:
  - kind: ServiceAccount
    name: platform-automation-sa
    namespace: platform-system
roleRef:
  kind: Role
  name: approved-client-ids-writer
  apiGroup: rbac.authorization.k8s.io
```

### Kyverno policy: Protect the ConfigMap itself

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: protect-approved-client-ids-configmap
spec:
  validationFailureAction: Enforce
  background: false
  rules:
    - name: block-configmap-modification
      match:
        any:
          - resources:
              kinds:
                - ConfigMap
              names:
                - approved-workload-identity-client-ids
              namespaces:
                - kyverno
      exclude:
        any:
          - subjects:
              - kind: ServiceAccount
                name: platform-automation-sa
                namespace: platform-system
      validate:
        message: "Only the platform automation service account can modify the approved client-ids ConfigMap."
        deny: {}
```

## 7. Rollout Plan

### Week 1: Inventory

```bash
# Step 1: Generate approved client-id lists across the management group
./generate-approved-client-ids.sh mg-platform ./approved/

# Step 2: Audit existing ServiceAccounts on each cluster
# Run against each cluster context:
kubectl get serviceaccounts --all-namespaces -o json \
  | jq -r '.items[] | select(.metadata.annotations."azure.workload.identity/client-id" != null) | "\(.metadata.namespace)/\(.metadata.name): \(.metadata.annotations."azure.workload.identity/client-id")"'

# Step 3: Cross-reference each client-id against the approved list for that cluster's environment
# Flag any SAs using client-ids from a different op-environment
```

**Blocking gate:** Understand all existing violations before deploying.

### Week 2: Deploy in Audit mode

1. Apply ConfigMaps to all clusters (`./apply-all-clusters.sh mg-platform ./approved/`)
2. Deploy Kyverno policy in `Audit` mode on all clusters
3. Review Kyverno policy reports for violations
4. Add missing legitimate client-ids to the approved lists

### Week 3: Harden and enforce

1. Deploy ConfigMap RBAC restrictions
2. Deploy ConfigMap protection Kyverno policy
3. Switch main policy to `Enforce` mode
4. Test: attempt to create SA with wrong-environment client-id, confirm denial

### Week 4: Automation

1. Integrate ConfigMap updates into UAMI provisioning pipeline
2. When a new UAMI is created with `op-environment=X`, automatically update ConfigMaps on all clusters where `op-environment=X`
3. Add monitoring for ConfigMap drift


## 10. Known Limitations

| Limitation | Impact | Mitigation |
|---|---|---|
| Annotation is not a security boundary | Pod can call Azure AD directly, bypassing annotation | Azure Policy is the real control; this catches misconfiguration |
| ConfigMap is separate from Azure Policy allowlist | Can drift out of sync | Both generated from same source script against management group |
| Kyverno fail-open risk | If Kyverno crashes, webhook fails open | `failurePolicy: Fail` + HA (3+ replicas) + health alerting |
| cluster-admin can disable webhook | Deliberate bypass | Alert on ValidatingWebhookConfiguration changes |
| System namespaces excluded from Kyverno | SAs in kube-system not validated | Explicitly list exclusions; accept or remove |
| New UAMIs need ConfigMap update | SA creation blocked until updated | Include in UAMI provisioning pipeline |
| Management group query needs Reader across all subs | Permission requirement | Use management group-scoped identity for the pipeline |
